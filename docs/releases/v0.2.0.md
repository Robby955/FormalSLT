## Intended release scope

  [candidate API policy](../api-stability.md).
- All-sample-size IID empirical-Bernstein PAC-Bayes, adaptive trajectory
  inference, and stationary Poisson and unknown-kernel certification.
- The opt-in 20-state random-refresh load
  [application](../random-refresh-load-application.md).
- Exact v0.1 example replay, downstream installation checks, declaration and
  axiom snapshots, theorem discovery, and literature/provenance documentation.

## Known boundaries

- The IID empirical-Bernstein endpoint is offline, not an optional-stopping
  theorem.
- Trajectory selection ranges over predictors and tilt atoms declared before
  scoring; it does not authorize post-outcome construction of new candidates.
- The named deterministic application path is not proved to belong to the
  theorem-produced good event, so that application step remains conditional.
- Normalized empirical-kernel radii require positive limiting row frequencies;
  candidate-kernel budget convergence additionally requires empirical
  discrepancy convergence.
- Application declarations are not part of the 19-name compatibility promise.
- Full continuous Dudley, all-real predictable tilt optimization, and
  continuous-state stationary Poisson certification remain open. See the
  [scope ledger](../assumptions-and-nonclaims.md).

## Publication gate

Before calling v0.2.0 released:

1. Enable immutable releases, protect `v*` tags from update/deletion, and
   require an approving PR review. On 2026-08-20 all three remained external
   governance gates: immutable releases were disabled, rulesets were empty,
   and branch protection required no review.
2. Put the release-artifact commits on the candidate PR, obtain substantive
   approval, merge, and record the exact resulting commit and tree.
3. Reserve a DOI in an unpublished archival deposit, add that reserved DOI and
   version to `CITATION.cff`, review the metadata delta, and pass the complete
   [release audit](../public-release-checklist.md) on the final exact commit.
   Reservation is not publication or a minted, resolving DOI.
4. Create protected tag `v0.2.0`. The automatic tag workflow requires its one
   remote resolution to equal the push event's exact commit, checks out that
   commit on Linux and macOS, and compares every subsequent tag lookup and Lake
   installation to the resolver outputs. Manual dispatch instead establishes
   one live resolution for the named existing tag.
5. Require both operating-system jobs plus the aggregate job. The aggregate
   requires matching tag/object/commit/tree receipts and rechecks the current
   remote. Receipts record identity and environment only; hosted job status is
   the build evidence.
6. Create the actual GitHub Release with both receipts and these boundaries,
   publish the archival deposit, and verify its DOI resolves to the same
   version, tag, commit, and tree.
7. Deploy the generated documentation and verify that source links are pinned
   to the released revision.

Only after steps 1--7 pass is this installation declaration valid:

```lean
require «formal-slt» from git
  "https://github.com/Robby955/FormalSLT.git" @ "v0.2.0"
```

Until then, use an exact reviewed commit as described in the
[README](../../README.md), and cite the current unversioned
[`CITATION.cff`](../../CITATION.cff) without claiming a v0.2 DOI.
